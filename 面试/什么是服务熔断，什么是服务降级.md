服务熔断和服务降级是微服务架构中保障系统稳定性的**核心容错机制**，两者常结合使用，但解决的问题和实现方式不同。以下是详细解析：

---

### **1. 服务熔断（Circuit Breaker）**
#### **定义**  
服务熔断是一种**主动保护机制**，当某个服务的故障率超过阈值时，系统会自动切断对该服务的调用，避免级联故障。  
**类比**：电路中的保险丝，电流过大时熔断以保护设备。

#### **触发条件**  
• 服务调用失败次数达到阈值（如连续5次失败）。  
• 错误率超过设定比例（如50%的请求超时或异常）。  

#### **核心流程**  
1. **关闭状态（Closed）**：正常调用服务，统计失败率。  
2. **打开状态（Open）**：触发熔断，直接拒绝请求，快速返回错误（如返回预设的降级结果）。  
3. **半开状态（Half-Open）**：熔断后经过一段时间，尝试放行少量请求探测服务是否恢复。  
   • 若成功：关闭熔断，恢复正常调用。  
   • 若失败：继续保持熔断状态。

#### **典型场景**  
• **依赖服务不可用**：例如支付服务宕机，触发熔断后直接返回“支付暂不可用”提示。  
• **网络波动**：第三方API响应超时，熔断避免线程阻塞。

#### **实现工具**  
• **Hystrix**（Netflix，已停更但广泛使用）  
• **Resilience4j**（轻量级替代方案）  
• **Sentinel**（阿里开源，支持动态规则配置）

---

### **2. 服务降级（Fallback）**
#### **定义**  
服务降级是**资源不足时的应急方案**，在系统高负载或部分服务异常时，暂时关闭非核心功能，确保核心流程可用。  
**核心思想**：牺牲次要功能，保障系统整体可用性。

#### **触发条件**  
• 系统资源紧张（如CPU、内存使用率超过80%）。  
• 服务响应时间过长（如超过5秒）。  
• 人工主动降级（如大促期间关闭商品评价功能）。

#### **实现方式**  
1. **返回默认值**：例如查询商品详情失败时，返回缓存中的基本信息。  
2. **简化流程**：下单时跳过风控校验，直接完成交易（后续补查）。  
3. **异步处理**：将请求写入队列，后续异步处理（如生成订单后延迟通知用户）。

#### **典型场景**  
• **秒杀活动**：降级商品详情页的推荐服务，优先保证下单功能。  
• **依赖服务超时**：调用物流服务超时后，降级为“物流信息稍后更新”。

#### **实现工具**  
• **Hystrix**：通过`@HystrixCommand(fallbackMethod = "methodName")`定义降级方法。  
• **Spring Cloud Gateway**：在网关层统一配置降级策略。  

---

### **3. 服务熔断 vs 服务降级：核心区别**
| **维度**         | **服务熔断**                          | **服务降级**                          |
|-------------------|---------------------------------------|---------------------------------------|
| **目标**          | 防止依赖服务故障导致系统崩溃          | 保障核心功能可用，牺牲非核心功能      |
| **触发条件**      | 依赖服务故障（如错误率、超时）        | 系统资源不足或主动降级                |
| **作用范围**      | 针对单个依赖服务                      | 可能影响多个服务或功能模块            |
| **实现方式**      | 自动触发（基于阈值）                  | 可自动或人工触发                      |
| **恢复机制**      | 半开状态探测依赖服务恢复              | 资源释放后自动恢复                    |

### **4. 实际应用中的协同使用**
#### **案例：电商下单流程**  
1. **正常流程**：  
   用户下单 → 校验库存 → 调用支付服务 → 生成订单 → 通知物流。  
2. **异常场景**：  
   • **支付服务超时**：触发熔断，直接拒绝支付请求。  
   • **降级方案**：记录订单为“待支付”状态，提示用户稍后重试。  
3. **结果**：  
   • 用户可继续浏览商品（核心功能不受影响）。  
   • 支付服务恢复后，熔断关闭，系统自动处理待支付订单。

#### **代码片段（Hystrix + Spring Boot）**  
```java
@Service
public class OrderService {
    
    @HystrixCommand(
        fallbackMethod = "createOrderFallback",  // 定义降级方法
        commandProperties = {
            @HystrixProperty(name = "circuitBreaker.requestVolumeThreshold", value = "5"),  // 触发熔断的最小请求数
            @HystrixProperty(name = "circuitBreaker.errorThresholdPercentage", value = "50") // 错误率阈值
        }
    )
    public Order createOrder(OrderRequest request) {
        // 调用支付服务（可能失败）
        boolean paymentSuccess = paymentService.process(request);
        if (!paymentSuccess) {
            throw new RuntimeException("支付失败");
        }
        return orderRepository.save(request.toOrder());
    }

    // 降级方法
    public Order createOrderFallback(OrderRequest request) {
        // 记录订单为“待支付”状态
        Order order = request.toOrder();
        order.setStatus(OrderStatus.PENDING);
        return orderRepository.save(order);
    }
}
```

### **5. 关键总结**
• **熔断是“止损”**：快速切断对故障服务的调用，防止雪崩效应。  
• **降级是“保底”**：在极端情况下确保核心功能可用。  
• **组合使用**：熔断触发后通常伴随降级，两者共同构建弹性系统。  
• **监控与调优**：需根据业务场景调整熔断阈值和降级策略（如错误率、超时时间）。
