在 MySQL 中，B+ 树索引的层级（深度）直接影响查询性能。以下通过一个 **具体示例** 详细说明索引深度与数据量的关系，以及为何单表数据量达到约 2000 万行时需关注性能风险。

---

### **一、B+ 树索引的结构**
以 InnoDB 引擎为例，B+ 树索引分为两种节点：
1. **非叶子节点**：存储键值（Key）和指向子节点的指针（Page Pointer）。
2. **叶子节点**：存储键值 + 数据行（主键索引）或键值 + 主键值（二级索引）。

每层节点的数量和容量决定了 B+ 树的深度。以下通过 **假设场景** 计算索引深度：

---

### **二、假设条件**
1. **页大小（Page Size）**：16KB（InnoDB 默认）。
2. **主键类型**：`INT`（4 字节）。
3. **非叶子节点条目**：每个条目 = 主键值（4 字节） + 指针（6 字节） = **10 字节**（实际可能有额外元数据，此处简化为 14 字节）。
4. **叶子节点容量**：单行数据大小 1KB，每页可存储约 **16 行**（16KB / 1KB = 16 行）。

---

### **三、索引深度与最大行数计算**
#### **1. 非叶子节点的容量**
每页存储的条目数 = 页大小 / 每个条目大小 = 16KB / 14 字节 ≈ **1170 个条目**。

#### **2. B+ 树层级与数据量关系**
• **层级 1（根节点）**：1 个非叶子页，指向 1170 个子页（层级 2）。
• **层级 2**：1170 个非叶子页，每个页指向 1170 个子页（层级 3）。
• **层级 3**：1170 × 1170 = 1,368,900 个叶子页，每页存储 16 行数据。

**总行数** = 叶子页数量 × 每页行数 = 1,368,900 × 16 ≈ **21,902,400 行**（约 2190 万行）。

---

### **四、索引深度对查询性能的影响**
• **查询流程**：  
  从根节点开始，逐层定位到叶子节点。  
  • 层级 1 → 层级 2 → 层级 3（共 3 次 I/O）。
• **性能关键点**：  
  • 若数据量超过约 2000 万行，B+ 树可能达到 **4 层**，查询需 4 次 I/O，性能显著下降。

---

### **五、不同场景的索引深度变化**
#### **1. 行大小更小（如 500 字节）**
• 每页存储行数 = 16KB / 500B ≈ 32 行。
• 总行数 = 1,368,900 × 32 ≈ **43,804,800 行**（约 4380 万行）。
• **结论**：行越小，单表可容纳更多数据，但超过阈值后仍需分表。

#### **2. 行大小更大（如 4KB）**
• 每页存储行数 = 16KB / 4KB = 4 行。
• 总行数 = 1,368,900 × 4 ≈ **5,475,600 行**（约 547 万行）。
• **结论**：大字段表需更早考虑分表或优化。

---

### **六、如何避免索引深度过高？**
1. **分库分表**：  
   • 按时间或哈希将数据拆分到多个物理表。  
   ```sql
   -- 按年份分表
   CREATE TABLE orders_2023 (id INT PRIMARY KEY, ...);
   CREATE TABLE orders_2024 (id INT PRIMARY KEY, ...);
   ```
2. **冷热数据分离**：  
   • 将历史数据迁移到归档表或分析型数据库（如 ClickHouse）。  
3. **使用覆盖索引**：  
   • 减少回表查询，降低对主键索引的依赖。  
   ```sql
   -- 覆盖索引示例
   CREATE INDEX idx_user_email ON users(email, name); -- 覆盖查询 SELECT email, name FROM users;
   ```

---

### **七、总结**
• **2000 万行阈值** 是基于典型场景（行大小 1KB、主键为 INT）的经验值，实际阈值需根据行大小、索引设计调整。  
• **核心原则**：B+ 树深度超过 3 层时，查询性能下降，需通过分表、归档或优化表结构控制单表数据量。
