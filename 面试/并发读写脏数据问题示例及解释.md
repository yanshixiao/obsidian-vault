### 并发读写脏数据问题示例及解释

以下是在 **先更新数据库，再删除缓存** 策略下，出现脏数据的场景示例：

---

#### **场景复现步骤**
1. **初始状态**：  
   • 数据库（主库）中某商品库存 `stock = 100`。  
   • 缓存中存储 `key=item:1001, value={stock: 100}`。  

2. **写请求（更新库存）**：  
   • **Step 1**：应用更新数据库，将 `stock` 改为 `80`（主库已更新，但从库同步延迟）。  
   • **Step 2**：删除缓存 `item:1001`。  

3. **读请求（并发读旧数据）**：  
   • 在 **主库已更新但从库未同步完成** 时，另一个读请求到达：  
     ◦ 缓存 `item:1001` 已被删除，触发回源查询。  
     ◦ 由于主从延迟，读请求访问从库，**读到旧值 `stock=100`**。  
     ◦ 将旧值 `{stock: 100}` 写入缓存。  

4. **结果**：  
   • 缓存中存储了旧数据 `stock=100`，而数据库实际值为 `80`，**数据不一致**。  

---

#### **核心原因**
1. **主从同步延迟**：  
   写请求更新主库后，从库可能未及时同步最新数据，导致读请求读到旧值。  
2. **缓存删除与回源查询的时序问题**：  
   删除缓存后，回源查询发生在从库同步完成前，写入旧数据到缓存。  

---

#### **解决方案**
1. **延迟双删（Double Delete）**：  
   • 写请求更新数据库后，先删除缓存。  
   • **延迟一段时间（如 1s）**，再次删除缓存。  
   • **目的**：确保主从同步完成，第二次删除清理可能的脏数据。  

   ```java
   public void updateStock(long itemId, int newStock) {
       // 1. 更新数据库（主库）
       db.update("UPDATE items SET stock=? WHERE id=?", newStock, itemId);
       // 2. 首次删除缓存
       cache.delete("item:" + itemId);
       // 3. 提交后延迟再次删除（异步执行）
       executor.schedule(() -> {
           cache.delete("item:" + itemId);
       }, 1, TimeUnit.SECONDS);
   }
   ```

2. **版本号/时间戳控制**：  
   • 数据写入缓存时携带版本号，读取时校验版本。  
   • 若版本号低于数据库，拒绝写入缓存。  

   ```java
   public void getItem(long itemId) {
       // 1. 从缓存读取数据
       CacheData cacheData = cache.get("item:" + itemId);
       // 2. 从数据库读取最新数据和版本号
       DBData dbData = db.query("SELECT stock, version FROM items WHERE id=?", itemId);
       // 3. 比较版本号
       if (cacheData == null || cacheData.version < dbData.version) {
           // 更新缓存
           cache.set("item:" + itemId, dbData);
       }
       return dbData;
   }
   ```

3. **串行化读写**：  
   • 对同一数据的读写请求，强制串行化处理（如分布式锁）。  
   • **缺点**：牺牲部分并发性能，适合强一致性场景。  

---

#### **总结**
• **先更新数据库，再删除缓存** 是主流方案，但需结合主从同步延迟、重试机制等处理边界问题。  
• **延迟双删** 是简单有效的补偿方案，**版本号控制** 能彻底解决一致性问题，但复杂度较高。  
• 设计时应根据业务容忍度选择最终一致性或强一致性策略。
