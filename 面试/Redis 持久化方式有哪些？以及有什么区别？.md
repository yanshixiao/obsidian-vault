Redis 提供了两种主要的持久化机制：**RDB（Redis Database）** 和 **AOF（Append-Only File）**，以及从 Redis 4.0 开始支持的混合持久化模式（RDB+AOF）。以下是它们的核心区别、优缺点及适用场景：

---

### **1. RDB（快照持久化）**
#### **机制**
- **原理**：定期将内存中的全量数据生成二进制快照（`dump.rdb` 文件），保存到磁盘。
- **触发条件**：
  - 手动触发：执行 `SAVE`（阻塞主线程）或 `BGSAVE`（后台异步保存）。
  - 自动触发：通过配置 `save <seconds> <changes>`（例如 `save 900 1` 表示 900 秒内至少 1 次修改则触发保存）。

#### **优点**
- **高性能**：生成 RDB 文件时通过子进程操作，主线程几乎无阻塞（仅 `BGSAVE`）。
- **紧凑高效**：RDB 文件是压缩的二进制格式，体积小，适合备份和灾难恢复。
- **快速恢复**：重启时加载 RDB 文件速度远快于 AOF。

#### **缺点**
- **数据丢失风险**：两次快照之间的数据可能丢失（取决于配置的保存频率）。
- **大文件生成开销**：数据量大时，生成 RDB 文件可能占用较多 CPU 和内存资源。

#### **配置示例**
```bash
# redis.conf
save 900 1       # 15 分钟内至少 1 次修改则保存
save 300 10      # 5 分钟内至少 10 次修改则保存
save 60 10000    # 1 分钟内至少 10000 次修改则保存
dbfilename dump.rdb
dir /var/lib/redis
```

---

### **2. AOF（追加日志持久化）**
#### **机制**
- **原理**：记录所有写操作命令（如 `SET`, `INCR`）到日志文件（`appendonly.aof`），重启时通过重放命令恢复数据。
- **写入策略**（`appendfsync` 配置）：
  - `always`：每条命令都同步刷盘（数据最安全，性能最低）。
  - `everysec`：每秒刷盘一次（默认，平衡性能与安全）。
  - `no`：由操作系统决定刷盘时机（性能最高，数据可能丢失）。

#### **优点**
- **高数据安全**：根据配置可做到秒级甚至实时持久化。
- **可读性强**：AOF 文件为文本格式，便于人工分析或修复。

#### **缺点**
- **文件体积大**：AOF 文件通常比 RDB 大（可通过 `AOF 重写` 优化）。
- **恢复速度慢**：重放所有命令恢复数据耗时较长。
- **写入开销**：高频写入时可能影响性能（尤其 `appendfsync always`）。

#### **AOF 重写**
- **目的**：压缩 AOF 文件体积，消除冗余命令（如多次 `SET` 同一 Key）。
- **触发方式**：
  - 手动触发：`BGREWRITEAOF`。
  - 自动触发：根据 `auto-aof-rewrite-percentage` 和 `auto-aof-rewrite-min-size` 配置。

#### **配置示例**
```bash
# redis.conf
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

---

### **3. 混合持久化（RDB + AOF）**（Redis 4.0+）
#### **机制**
- **原理**：结合 RDB 和 AOF 的优势：
  - 定期生成 RDB 快照作为全量备份。
  - 两次 RDB 之间的增量数据通过 AOF 日志记录。
  - **重启恢复时**：先加载 RDB 文件，再重放 AOF 增量命令。
- **触发条件**：需同时开启 RDB 和 AOF，并通过配置启用混合模式。

#### **优点**
- **快速恢复**：RDB 提供全量数据，减少 AOF 重放时间。
- **数据安全**：AOF 记录增量操作，降低数据丢失风险。

#### **配置示例**
```bash
# redis.conf
aof-use-rdb-preamble yes  # 启用混合持久化
```

---

### **RDB vs AOF vs 混合模式对比**
| **特性**          | **RDB**                  | **AOF**                  | **混合模式（RDB+AOF）**    |
|-------------------|--------------------------|--------------------------|---------------------------|
| **数据安全性**    | 可能丢失最后一次快照后的数据 | 根据 `appendfsync` 配置，可做到秒级或实时安全 | 接近 AOF 的安全性         |
| **文件体积**      | 小（二进制压缩）         | 大（文本日志）           | 中等（RDB 全量 + AOF 增量）|
| **恢复速度**      | 快                       | 慢                       | 较快（优先加载 RDB）       |
| **性能影响**      | 生成快照时短暂阻塞       | 高频写入时可能影响性能   | 类似 AOF                  |
| **适用场景**      | 允许数据丢失的备份场景   | 对数据安全性要求高的场景 | 平衡安全性与恢复速度       |

---

### **如何选择持久化方式？**
1. **高数据安全**：优先选择 **AOF**（`appendfsync everysec` 或 `always`）。
2. **快速恢复与备份**：选择 **RDB**（定期快照）。
3. **平衡场景**：使用 **混合模式**（Redis 4.0+），兼顾安全性和恢复效率。
4. **禁用持久化**：若仅作缓存且允许数据丢失，可关闭持久化（`save ""`）。

---

### **总结**
- **RDB** 适合备份和快速恢复，但存在数据丢失风险。
- **AOF** 提供更高的数据安全性，但文件体积大且恢复慢。
- **混合模式** 结合两者优势，是现代 Redis 部署的推荐方案。  
根据业务需求合理配置持久化策略，是保障 Redis 数据可靠性和性能的关键。
