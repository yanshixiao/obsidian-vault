在 Seata 的 **AT（自动补偿）模式** 中，**全局锁** 是确保分布式事务 **隔离性** 的核心机制。它通过 **数据库行级锁** 实现，目的是防止其他事务在分布式事务未提交时修改相同数据，避免脏读或脏写。以下是其工作原理和关键细节：

---

### **一、全局锁的作用**
1. **解决脏读**：  
   确保在事务执行过程中，其他事务无法读取到未提交的中间状态数据。  
2. **防止脏写**：  
   防止其他事务修改当前事务正在操作的数据，保证操作原子性。

---

### **二、全局锁的实现机制**
#### **1. 锁的获取与释放**
• **获取锁**：  
  当 AT 模式的事务分支（分支事务）执行 `UPDATE` 或 `DELETE` 操作时，Seata 会通过 **`SELECT FOR UPDATE`** 语句对操作的数据行加锁（全局锁）。  
  ```sql
  -- Seata 自动生成的加锁语句（示例）
  SELECT * FROM account WHERE id = 1 FOR UPDATE;
  ```
• **释放锁**：  
  全局锁在事务提交或回滚后释放。若事务提交，锁释放；若回滚，执行反向 SQL（如 `undo_log` 中的补偿 SQL）后释放。

#### **2. 锁的存储**
• **存储位置**：  
  全局锁信息存储在 Seata 的 **全局事务协调器（TC）** 中，而非数据库本身。  
• **锁的粒度**：  
  锁的粒度是 **行级锁**，通过 `主键` 或 `唯一索引` 定位具体行。

---

### **三、全局锁的工作流程
以转账场景为例（账户A向账户B转账100元）：

1. **事务分支1（扣减账户A余额）**：
   ```sql
   UPDATE account SET balance = balance - 100 WHERE id = 1;
   ```
   • Seata 自动生成 `SELECT FOR UPDATE` 锁定账户A的数据行。

2. **事务分支2（增加账户B余额）**：
   ```sql
   UPDATE account SET balance = balance + 100 WHERE id = 2;
   ```
   • Seata 自动生成 `SELECT FOR UPDATE` 锁定账户B的数据行。

3. **全局事务提交**：
   • 所有分支事务成功后，TC 通知各分支提交，释放全局锁。

4. **全局事务回滚**：
   • 若任一分支失败，TC 触发补偿（执行反向 SQL），完成后释放锁。

---

### **四、全局锁的优缺点**
#### **优点**：
• **自动管理**：开发者无需手动处理锁逻辑，降低编码复杂度。
• **行级锁粒度**：锁竞争范围小，对性能影响可控（相比表级锁）。

#### **缺点**：
• **锁竞争风险**：高并发场景下，多个事务同时操作同一行数据会导致锁等待超时（默认30秒）。
• **依赖数据库特性**：需数据库支持 `SELECT FOR UPDATE`（如 MySQL、Oracle），不兼容某些 NoSQL 数据库。

---

### **五、如何优化全局锁问题？**
1. **减少锁持有时间**：  
   • 优化 SQL 性能，避免长事务。
   • 将耗时操作（如 RPC 调用）移到事务外。

2. **调整锁超时时间**：  
   ```properties
   # seata-server 配置文件（seata.properties）
   store.db.global.lock.queryTimeout=5000 # 锁查询超时时间（默认30秒）
   ```

3. **避免热点数据**：  
   • 通过分库分表分散数据，减少单行并发压力。
   • 使用业务设计规避（如异步冲正、消息队列削峰）。

4. **切换事务模式**：  
   • 对强一致性场景，改用 **TCC 模式**（手动控制资源预留和提交）。  
   • 对长事务场景，改用 **Saga 模式**（异步补偿，无锁）。

---

### **六、全局锁与本地锁的区别**
| **维度**       | **全局锁**                          | **本地锁（如数据库行锁）**          |
|----------------|-------------------------------------|-----------------------------------|
| **作用范围**   | 跨服务、跨数据库的分布式锁            | 单数据库内行级锁                   |
| **管理方**     | Seata 事务协调器（TC）               | 数据库自身（如 MySQL InnoDB）       |
| **隔离级别**   | 默认读未提交（通过全局锁隔离写操作）   | 依赖数据库隔离级别（如读已提交）     |
