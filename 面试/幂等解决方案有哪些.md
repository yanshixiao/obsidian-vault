以下是常见的幂等解决方案及其详细说明：

---

### 一、**唯一标识符（Unique ID）**
#### **原理**  
为每个请求生成全局唯一ID（如UUID、雪花算法ID），服务端通过该ID判断请求是否已处理。  
#### **实现**  
1. **客户端生成ID**：客户端在请求时携带唯一ID（如 `X-Request-Id`）。  
2. **服务端校验**：服务端存储已处理的ID（如Redis或数据库），处理前检查是否存在。  
```java
public boolean processRequest(String requestId, RequestData data) {
    if (redis.exists("processed:" + requestId)) {
        return false; // 已处理，直接返回
    }
    // 执行业务逻辑
    boolean success = businessService.process(data);
    if (success) {
        redis.setex("processed:" + requestId, 3600, "1"); // 存储1小时
    }
    return success;
}
```
#### **适用场景**  
• API请求（如支付、订单提交）。  
• 消息队列消费（如Kafka消费者去重）。  

#### **优缺点**  
• **优点**：实现简单，通用性强。  
• **缺点**：需存储大量ID，可能增加Redis/DB压力。

### 二、**数据库唯一约束**
#### **原理**  
利用数据库的唯一索引或主键，防止重复插入数据。  
#### **实现**  
```sql
CREATE TABLE orders (
    order_id VARCHAR(64) PRIMARY KEY, -- 唯一订单号
    user_id INT,
    amount DECIMAL
);
```
• 插入时若唯一键冲突，直接忽略或返回已有结果。  
```java
try {
    orderRepository.save(order); // 若order_id冲突，抛出DuplicateKeyException
} catch (DuplicateKeyException e) {
    return "订单已存在";
}
```
#### **适用场景**  
• 数据插入操作（如订单创建、用户注册）。  

#### **优缺点**  
• **优点**：无需额外代码，依赖数据库能力。  
• **缺点**：仅适用于插入场景，无法解决更新操作的幂等性。

---

### 三、**版本号/乐观锁**
#### **原理**  
为数据记录增加版本号字段，更新时校验版本号是否匹配。  
#### **实现**  
1. **数据库表设计**：  
   ```sql
   ALTER TABLE inventory ADD version INT DEFAULT 0;
   ```
2. **更新时检查版本**：  
   ```sql
   UPDATE inventory SET stock = stock - 10, version = version + 1 
   WHERE item_id = 'item_001' AND version = 1;
   ```
3. **代码逻辑**：  
   ```java
   public boolean deductStock(String itemId, int quantity, int currentVersion) {
       int rows = jdbcTemplate.update(
           "UPDATE inventory SET stock = stock - ?, version = version + 1 " +
           "WHERE item_id = ? AND version = ?", 
           quantity, itemId, currentVersion
       );
       return rows > 0;
   }
   ```
#### **适用场景**  
• 并发更新操作（如库存扣减、账户余额变更）。  

#### **优缺点**  
• **优点**：避免并发覆盖，保证数据一致性。  
• **缺点**：需维护版本字段，高并发时可能重试频繁。

### 四、**Token机制**
#### **原理**  
客户端先获取一个临时Token，提交请求时携带该Token，服务端验证后使Token失效。  
#### **实现**  
1. **获取Token**：  
   ```java
   public String createToken() {
       String token = UUID.randomUUID().toString();
       redis.setex("token:" + token, 60, "1"); // Token有效期60秒
       return token;
   }
   ```
2. **提交请求**：  
   客户端在请求头中携带 `X-Token: <token>`。  
3. **验证Token**：  
   ```java
   public boolean processWithToken(String token, RequestData data) {
       if (!redis.exists("token:" + token)) {
           return false; // Token无效或已使用
       }
       boolean success = businessService.process(data);
       if (success) {
           redis.del("token:" + token); // 删除Token
       }
       return success;
   }
   ```
#### **适用场景**  
• 防止表单重复提交。  
• 支付确认等需用户主动触发的操作。  

#### **优缺点**  
• **优点**：安全性高，有效防止重复提交。  
• **缺点**：需额外获取Token的步骤，增加交互次数。

### 五、**状态机（State Machine）**
#### **原理**  
业务操作设计为状态流转，只有特定状态下才允许执行操作。  
#### **实现**  
1. **定义状态**：  
   ```java
   public enum OrderStatus {
       PENDING, PAID, CANCELED, DELIVERED
   }
   ```
2. **状态校验**：  
   ```java
   public void payOrder(String orderId) {
       Order order = orderRepository.findById(orderId);
       if (order.getStatus() != OrderStatus.PENDING) {
           throw new IllegalStateException("订单无法支付");
       }
       order.setStatus(OrderStatus.PAID);
       orderRepository.save(order);
   }
   ```
#### **适用场景**  
• 订单状态流转（如支付→发货→完成）。  
• 工单审批流程。  

#### **优缺点**  
• **优点**：业务逻辑清晰，天然支持幂等。  
• **缺点**：需设计合理的状态机，复杂度较高。

### 六、**去重表（Deduplication Table）**
#### **原理**  
单独维护一张表记录已处理的请求ID，处理前先查询是否重复。  
#### **实现**  
1. **表结构**：  
   ```sql
   CREATE TABLE processed_requests (
       request_id VARCHAR(64) PRIMARY KEY,
       created_time DATETIME
   );
   ```
2. **处理逻辑**：  
   ```java
   @Transactional
   public void handleRequest(String requestId, RequestData data) {
       if (processedRequestsRepository.existsById(requestId)) {
           return; // 已处理
       }
       businessService.process(data);
       processedRequestsRepository.save(new ProcessedRequest(requestId));
   }
   ```
#### **适用场景**  
• 异步任务处理（如定时任务、消息队列消费）。  

#### **优缺点**  
• **优点**：隔离业务数据，逻辑简单。  
• **缺点**：表数据量可能膨胀，需定期清理。

---

### 七、**消息队列去重**
#### **原理**  
利用消息队列的消息ID或业务唯一键，在消费端实现去重。  
#### **实现（以Kafka为例）**  
1. **生产者**：  
   ```java
   ProducerRecord<String, String> record = new ProducerRecord<>("orders", orderId, data);
   producer.send(record);
   ```
2. **消费者**：  
   ```java
   @KafkaListener(topics = "orders")
   public void consume(String orderId, String data) {
       if (redis.setnx("dedup:" + orderId, "1") == 0) {
           return; // 已消费
       }
       businessService.process(data);
       redis.expire("dedup:" + orderId, 3600); // 保留1小时
   }
   ```
#### **适用场景**  
• 消息队列消费（如订单处理、日志处理）。  

#### **优缺点**  
• **优点**：天然支持消息去重。  
• **缺点**：依赖消息队列特性（如Kafka的 `enable.idempotence=true`）。

---

### 八、**HTTP方法语义**
#### **原理**  
利用HTTP方法的幂等性设计API（如PUT、DELETE）。  
#### **实现**  
• **PUT**：重复更新同一资源，结果一致。  
• **DELETE**：重复删除同一资源，结果一致。  
```java
@PutMapping("/users/{id}")
public User updateUser(@PathVariable String id, @RequestBody User user) {
    // 无论调用多少次，结果相同
    return userService.update(id, user);
}
```
#### **适用场景**  
• RESTful API设计（如资源更新、删除）。  

#### **优缺点**  
• **优点**：符合HTTP标准，减少重复提交问题。  
• **缺点**：仅适用于特定语义的接口。

### **总结与选型建议**
| **方案**          | **适用场景**                     | **优点**                          | **缺点**                          |  
|-------------------|--------------------------------|----------------------------------|----------------------------------|  
| **唯一标识符**      | 通用请求去重（如支付、API调用）     | 简单灵活                          | 需存储ID，可能占用资源              |  
| **数据库唯一约束**  | 数据插入（如订单、用户）           | 无需额外代码                      | 仅适用于插入操作                   |  
| **乐观锁**         | 并发更新（如库存扣减）             | 避免数据覆盖                      | 需维护版本号，高并发时重试频繁       |  
| **Token机制**     | 防止重复提交（如表单、支付）        | 安全性高                          | 需多次交互                         |  
| **状态机**         | 业务流程（如订单状态流转）         | 业务逻辑清晰                      | 设计复杂度高                       |  
| **去重表**         | 异步任务处理                      | 隔离业务数据                      | 表数据膨胀                         |  
| **消息队列去重**    | 消息消费（如Kafka、RabbitMQ）     | 天然去重                          | 依赖MQ特性                        |  
| **HTTP方法语义**   | RESTful API设计                | 符合标准                          | 仅适用于特定方法                    |  

**最佳实践**：  
• **组合使用**：如订单创建使用“数据库唯一约束+状态机”，支付接口使用“唯一ID+乐观锁”。  
• **定期清理**：针对存储唯一ID或Token的方案，设置合理的过期时间。  
• **监控报警**：跟踪去重失败率，及时发现异常重复请求。
