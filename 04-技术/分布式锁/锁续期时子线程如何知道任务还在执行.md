在分布式锁的续期机制中，判断业务代码是否仍在执行的核心思路是：通过某种方式跟踪业务线程的状态。以下是几种常见实现方法及其原理：

---

### **方法一：通过线程状态检查**
**原理**
• 在业务代码执行时，记录当前线程的引用。

• 续期线程通过检查该线程是否存活（`isAlive()`）或是否处于运行状态，判断业务是否仍在执行。


**代码示例**
```java
public class RedisDistributedLock {
    private Thread businessThread; // 记录业务线程的引用

    public boolean tryLock(...) {
        // 加锁逻辑...
        businessThread = Thread.currentThread(); // 记录当前业务线程
        startRenewThread();
        return true;
    }

    private void renewLock() {
        if (businessThread != null && businessThread.isAlive()) {
            // 业务线程仍在运行，续期锁
            jedis.pexpire(lockKey, expireTime);
        }
    }
}
```

**缺点**
• 如果业务代码中存在线程阻塞（如 `sleep`、`wait`）或线程池复用，`isAlive()` 可能无法准确反映业务逻辑是否完成。

• 不适用于异步回调模式（如 `CompletableFuture`）。


---

### **方法二：通过业务状态标志**
**原理**
• 在业务代码中插入一个状态标志（如 `AtomicBoolean`），业务执行完成后主动更新标志。

• 续期线程定期检查该标志，决定是否续期。


**代码示例**
```java
public class BusinessService {
    private AtomicBoolean isExecuting = new AtomicBoolean(false);

    public void executeBusiness() {
        isExecuting.set(true);
        try {
            // 业务逻辑代码...
        } finally {
            isExecuting.set(false); // 确保最终清理标志
        }
    }

    public boolean isExecuting() {
        return isExecuting.get();
    }
}

// 在续期线程中检查标志
private void renewLock() {
    if (businessService.isExecuting()) {
        jedis.pexpire(lockKey, expireTime);
    }
}
```

**缺点**
• 需要业务代码主动配合设置和清理标志，存在遗漏风险（如业务代码未执行 `finally` 块）。

• 不适用于第三方库或框架控制的业务逻辑。


---

### **方法三：通过 Future 对象**
**原理**
• 如果业务逻辑是异步执行的，可以通过 `Future` 对象检查任务是否完成。

• 续期线程通过 `future.isDone()` 判断是否需要续期。


**代码示例**
```java
public class RedisDistributedLock {
    private Future<?> future; // 异步任务引用

    public void executeAsyncBusiness() {
        future = executor.submit(() -> {
            // 业务逻辑代码...
        });
        startRenewThread();
    }

    private void renewLock() {
        if (!future.isDone()) {
            jedis.pexpire(lockKey, expireTime);
        }
    }
}
```

**缺点**
• 仅适用于异步任务，不适用于同步阻塞场景。


---

### **方法四：通过回调机制**
**原理**
• 业务代码执行完成后，主动调用回调函数通知续期线程停止。

• 续期线程通过一个 `volatile` 变量或原子变量控制循环终止。


**代码示例**
```java
public class RedisDistributedLock {
    private volatile boolean shouldRenew = true;

    public void executeBusiness() {
        try {
            // 业务逻辑代码...
        } finally {
            shouldRenew = false; // 通知续期线程停止
        }
    }

    private void renewLock() {
        while (shouldRenew) {
            jedis.pexpire(lockKey, expireTime);
            Thread.sleep(expireTime / 3);
        }
    }
}
```

**缺点**
• 需要业务代码主动触发回调，对业务代码侵入性较高。


---

### **方法五：超时机制（兜底方案）**
**原理**
• 不严格检查业务是否执行，而是根据锁的剩余生存时间动态续期。

• 如果业务执行时间超过预期，锁会自动过期（最终兜底）。


**代码示例**
```java
private void renewLock() {
    long ttl = jedis.pttl(lockKey); // 获取锁的剩余生存时间
    if (ttl < expireTime / 2) { // 当剩余时间不足一半时续期
        jedis.pexpire(lockKey, expireTime);
    }
}
```

**缺点**
• 无法精准控制续期时机，可能造成不必要的续期开销。


---

### **最佳实践：组合方案**
1. 优先使用业务状态标志 + 线程状态检查：  
   通过 `AtomicBoolean` 标志明确业务状态，结合线程存活状态兜底。
2. 异步任务使用 Future：  
   如果业务是异步的，直接依赖 `Future.isDone()`。
3. 超时机制作为最后防线：  
   即使业务未完成，锁也会在超时后自动释放，避免死锁。

---

### **关键注意事项**
1. 线程安全：  
   状态标志或 `Future` 对象必须是线程安全的（如 `AtomicBoolean`、`volatile`）。
2. 异常处理：  
   业务代码必须通过 `try-finally` 确保状态标志的清理。
3. 资源释放：  
   续期线程必须在业务完成后及时停止，避免空转消耗 CPU。

---

通过上述方法，续期线程可以可靠地判断业务是否仍在执行，从而决定是否续期锁。实际选择需根据业务场景的同步/异步特性、代码侵入性等因素综合权衡。
