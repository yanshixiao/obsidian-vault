在 Spring 框架中，**事务传播级别（Transaction Propagation）** 定义了**多个事务方法相互调用时，事务如何传播和嵌套**的规则。它解决的核心问题是：当一个事务方法调用另一个事务方法时，事务的边界应如何界定？例如，是否沿用现有事务、挂起当前事务、抛出异常等。

以下是 Spring 定义的 **7 种事务传播级别**，按常用性排序：

---

### **1. REQUIRED（默认）**
- **规则**：  
  - 如果当前存在事务，则加入该事务。  
  - 如果当前没有事务，则新建一个事务。
- **适用场景**：大多数业务方法（如订单创建、库存扣减）。
- **示例**：  
  ```java
  @Transactional(propagation = Propagation.REQUIRED)
  public void methodA() {
      methodB(); // methodB 加入 methodA 的事务
  }
  ```

---

### **2. REQUIRES_NEW**
- **规则**：  
  - 无论当前是否存在事务，都新建一个独立事务。  
  - 若当前有事务，则挂起（暂停）原事务，直到新事务完成。
- **特点**：  
  - 新事务与外层事务完全隔离，互不影响（各自独立提交或回滚）。  
  - 适用于需要强制记录日志、审计等场景。
- **示例**：  
  ```java
  @Transactional(propagation = Propagation.REQUIRES_NEW)
  public void logOperation() {
      // 即使外层事务回滚，此日志仍会提交
  }
  ```

---

### **3. NESTED**
- **规则**：  
  - 如果当前存在事务，则在嵌套事务（子事务）中执行。  
  - 如果当前没有事务，则新建一个事务（行为同 REQUIRED）。  
- **特点**：  
  - **嵌套事务是外层事务的一部分**：子事务回滚不影响外层事务，但外层事务回滚会连带子事务回滚。  
  - **依赖数据库的保存点（Savepoint）** 实现（如 MySQL 的 InnoDB 引擎支持）。  
- **适用场景**：允许部分操作独立回滚，但整体依赖主事务（如批量处理中的部分失败回滚）。  
- **示例**：  
  ```java
  @Transactional(propagation = Propagation.NESTED)
  public void batchProcess() {
      // 若失败，仅回滚到此保存点，外层事务可继续
  }
  ```

---

### **4. SUPPORTS**
- **规则**：  
  - 如果当前存在事务，则加入该事务。  
  - 如果当前没有事务，则以非事务方式执行。
- **适用场景**：查询方法，允许在事务或非事务环境下执行（如只读操作）。

---

### **5. NOT_SUPPORTED**
- **规则**：  
  - 总是以非事务方式执行。  
  - 如果当前存在事务，则挂起该事务。
- **适用场景**：强制在非事务环境执行（如某些不涉及数据修改的第三方接口调用）。

---

### **6. MANDATORY**
- **规则**：  
  - 必须在一个已存在的事务中运行，否则抛出异常。
- **适用场景**：强制要求调用方必须开启事务（如关键数据更新方法）。

---

### **7. NEVER**
- **规则**：  
  - 必须在非事务环境下执行，如果当前存在事务，则抛出异常。
- **适用场景**：确保方法不在事务中执行（如某些性能敏感的只读操作）。

---

### **对比总结**
| **传播级别**      | 当前有事务 | 当前无事务              | 特点                           |
|-------------------|------------|-------------------------|-------------------------------|
| **REQUIRED**      | 加入事务   | 新建事务                | 默认选择，适合大多数场景        |
| **REQUIRES_NEW**  | 挂起并新建 | 新建事务                | 独立事务，完全隔离              |
| **NESTED**        | 嵌套事务   | 新建事务（同 REQUIRED） | 依赖外层事务，可部分回滚        |
| **SUPPORTS**      | 加入事务   | 非事务执行              | 灵活适应调用方的事务状态        |
| **NOT_SUPPORTED** | 挂起事务   | 非事务执行              | 强制非事务环境                  |
| **MANDATORY**     | 加入事务   | 抛出异常                | 强制要求存在事务                |
| **NEVER**         | 抛出异常   | 非事务执行              | 强制要求无事务                  |

---

### **关键区别：NESTED vs REQUIRES_NEW**
| **维度**       | **NESTED**                     | **REQUIRES_NEW**               |
|----------------|--------------------------------|--------------------------------|
| **事务关系**   | 嵌套在外层事务中              | 完全独立的新事务               |
| **回滚影响**   | 外层事务回滚导致子事务回滚     | 外层事务回滚不影响新事务        |
| **实现机制**   | 数据库保存点（Savepoint）      | 独立事务上下文                 |
| **性能开销**   | 较低                          | 较高（需挂起和恢复事务）        |

---

### **代码示例**
```java
@Service
public class OrderService {

    @Autowired
    private LogService logService;

    // 默认 REQUIRED
    @Transactional
    public void createOrder(Order order) {
        // 业务逻辑
        logService.auditLog(order); // 调用 REQUIRES_NEW 方法
    }
}

@Service
public class LogService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void auditLog(Order order) {
        // 记录审计日志（独立事务）
    }
}
```

---

### **如何选择传播级别？**
1. **默认使用 REQUIRED**：覆盖多数需要事务的方法。
2. **需要独立事务时用 REQUIRES_NEW**：如日志记录、异步事件处理。
3. **部分回滚需求用 NESTED**：如批量处理中的单条失败回滚。
4. **强制事务环境用 MANDATORY**：确保方法不被非事务调用。
5. **非事务操作用 NOT_SUPPORTED/NEVER**：优化性能或避免事务副作用。

---

### **注意事项**
- **数据库兼容性**：`NESTED` 依赖数据库的保存点支持（如 MySQL InnoDB 支持，Oracle 不支持）。
- **性能影响**：`REQUIRES_NEW` 会频繁挂起和恢复事务，增加开销。
- **事务超时**：外层事务的超时设置可能影响嵌套事务的行为。
