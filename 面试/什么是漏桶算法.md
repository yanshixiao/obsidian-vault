漏桶算法（Leaky Bucket Algorithm）是一种用于流量整形（Traffic Shaping）和速率限制（Rate Limiting）的经典算法，其核心思想是通过“恒定速率”处理请求，平滑突发流量，保护系统免受过载影响。

---

### **核心原理**
1. **桶的容量**：桶的容量固定，表示系统可处理的**最大积压请求数**。  
2. **漏水速率**：桶底以**恒定速率**漏水（处理请求），无论流入速度多快，流出速率恒定。  
3. **请求处理逻辑**：  
   • 若桶未满，请求被暂存到桶中（排队等待处理）。  
   • 若桶已满，新请求被拒绝（触发限流）。  

---

### **关键参数**
| **参数**       | **说明**                          | **示例**              |
|----------------|-----------------------------------|----------------------|
| 桶容量（Capacity） | 桶能容纳的最大请求数               | 1000个请求            |
| 漏水速率（Rate）  | 桶每秒处理的请求数（恒定速率）       | 10请求/秒             |

---

### **算法流程**
```plaintext
1. 请求到达 → 检查桶是否有空间  
   ↓  
2. 若桶未满 → 请求入桶并排队等待处理  
   ↓  
3. 桶底以固定速率漏水（处理请求）  
   ↓  
4. 若桶已满 → 拒绝新请求  
```

---

### **Java 实现示例**
```java
public class LeakyBucketLimiter {
    private final long capacity;      // 桶容量
    private final long rateMillis;   // 漏水速率（毫秒/请求）
    private long water = 0;          // 当前水量（积压请求数）
    private long lastLeakTime = System.currentTimeMillis(); // 上次漏水时间

    public LeakyBucketLimiter(int capacity, int ratePerSecond) {
        this.capacity = capacity;
        this.rateMillis = 1000 / ratePerSecond; // 转换为每请求所需毫秒
    }

    public synchronized boolean allow() {
        long now = System.currentTimeMillis();
        // 计算漏水量：经过时间 / 每请求时间 → 漏水量
        long elapsed = now - lastLeakTime;
        long leaks = elapsed / rateMillis;
        if (leaks > 0) {
            water = Math.max(0, water - leaks); // 漏水量不超过当前水量
            lastLeakTime = now;
        }
        // 检查桶容量
        if (water < capacity) {
            water++;
            return true; // 允许请求
        }
        return false; // 限流
    }
}

// 使用示例：每秒处理10个请求，桶容量1000
LeakyBucketLimiter limiter = new LeakyBucketLimiter(1000, 10);
if (limiter.allow()) {
    // 处理请求
} else {
    // 限流
}
```

### **应用场景**
1. **网络流量整形**：平滑网络数据包发送速率，避免拥塞。  
2. **API限流**：保护后端服务，避免突发流量击穿系统。  
3. **消息队列消费**：控制消费者处理消息的速率，防止数据库过载。  

---

### **优缺点对比**
| **优点**                          | **缺点**                          |
|----------------------------------|----------------------------------|
| 1. **流量绝对平滑**：输出速率恒定，适合稳定处理场景。 | 1. **无法应对突发流量**：突发请求需排队等待，可能增加延迟。 |
| 2. **内存可控**：桶容量限制最大积压请求数。        | 2. **灵活性不足**：无法根据系统负载动态调整速率。       |

---

### **与令牌桶算法的区别**
| **维度**       | **漏桶算法**                          | **令牌桶算法**                      |
|----------------|--------------------------------------|------------------------------------|
| **流量特性**    | 恒定速率输出，平滑突发流量              | 允许短期突发流量（桶内令牌可累积）       |
| **核心控制点**  | 控制流出速率                           | 控制流入速率（通过生成令牌）            |
| **适用场景**    | 需严格速率控制的场景（如音视频流）        | 需兼顾突发和平稳的场景（如API网关）      |

---

### **总结**
漏桶算法通过**强制恒定速率处理请求**，确保系统负载稳定，适用于需要**严格流量整形**的场景。尽管其灵活性较低，但在网络传输、金融交易等对稳定性要求极高的领域仍有广泛应用。实际开发中，可结合监控系统动态调整参数（如桶容量和速率），以适应业务变化。
