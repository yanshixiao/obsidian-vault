针对大表的优化，需从 **查询性能**、**存储效率** 和 **架构设计** 多维度入手。以下是系统化的优化方案，涵盖核心策略与实操示例：

---

### **一、索引优化（低成本高效方案）**
#### **1. 避免全表扫描**
• **添加必要索引**：对高频查询的 `WHERE`、`JOIN`、`ORDER BY` 字段建索引。
  ```sql
  ALTER TABLE big_table ADD INDEX idx_user_id (user_id);
  ```
• **复合索引优化**：遵循最左前缀原则，优先覆盖高频查询。
  ```sql
  -- 针对 WHERE a=? AND b=? ORDER BY c 的查询
  ALTER TABLE big_table ADD INDEX idx_a_b_c (a, b, c);
  ```

#### **2. 索引维护**
• **删除冗余索引**：通过 `SHOW INDEX FROM big_table` 分析使用率低的索引。
  ```sql
  ALTER TABLE big_table DROP INDEX unused_idx;
  ```
• **监控碎片化**：定期优化表（避免高峰期操作）。
  ```sql
  OPTIMIZE TABLE big_table;
  ```

#### **3. 覆盖索引**
• 将查询字段全部包含在索引中，减少回表查询。
  ```sql
  -- 查询只需 user_id 和 status 字段
  ALTER TABLE big_table ADD INDEX idx_user_status (user_id, status);
  ```

---

### **二、表结构优化**
#### **1. 垂直拆分（冷热分离）**
• **拆分大字段**：将 `TEXT`、`BLOB` 等字段拆分到副表。
  ```sql
  -- 主表保留核心字段
  CREATE TABLE big_table_main (
    id INT PRIMARY KEY,
    user_id INT,
    created_at DATETIME,
    INDEX idx_user_id (user_id)
  );
  
  -- 副表存储大字段
  CREATE TABLE big_table_extra (
    id INT PRIMARY KEY,
    content TEXT,
    FOREIGN KEY (id) REFERENCES big_table_main(id)
  );
  ```

#### **2. 字段类型优化**
• **缩小字段类型**：如 `INT(11)` → `SMALLINT`，`VARCHAR(255)` → `VARCHAR(64)`。
• **使用时间戳替代 DATETIME**：`TIMESTAMP` 占 4 字节，`DATETIME` 占 8 字节。

---

### **三、分库分表（应对亿级数据）**
#### **1. 水平分表**
• **按范围分表**：如按时间（每月一张表）。
  ```sql
  CREATE TABLE big_table_202301 (LIKE big_table);
  CREATE TABLE big_table_202302 (LIKE big_table);
  ```
• **按哈希分表**：均匀分布数据。
  ```sql
  -- 以 user_id 的哈希值分 16 张表
  CREATE TABLE big_table_00 (LIKE big_table);
  ...
  CREATE TABLE big_table_15 (LIKE big_table);
  ```

#### **2. 分库分表中间件**
• **工具选型**：ShardingSphere、Vitess、MyCat。
• **路由逻辑**：通过中间件透明化分片规则，应用无感知。
  ```yaml
  # ShardingSphere 配置示例
  rules:
    - !SHARDING
      tables:
        big_table:
          actualDataNodes: ds_${0..1}.big_table_${0..15}
          databaseStrategy:
            standard:
              shardingColumn: user_id
              shardingAlgorithmName: db_hash
          tableStrategy:
            standard:
              shardingColumn: user_id
              shardingAlgorithmName: table_hash
  ```

---

### **四、读写分离与缓存**
#### **1. 读写分离**
• **主从架构**：主库处理写操作，从库负载读请求。
  ```sql
  -- 应用层配置数据源
  spring.datasource.master.url=jdbc:mysql://master:3306/db
  spring.datasource.slave.url=jdbc:mysql://slave:3306/db
  ```

#### **2. 缓存加速**
• **Redis 缓存热点数据**：缓存查询结果或常用字段。
  ```java
  // 伪代码：查询优先走缓存
  String key = "user:" + userId;
  String data = redis.get(key);
  if (data == null) {
      data = db.query("SELECT * FROM big_table WHERE user_id=?", userId);
      redis.setex(key, 3600, data);
  }
  ```

---

### **五、数据归档与清理**
#### **1. 历史数据归档**
• **定时任务迁移旧数据**：将非活跃数据移至历史表。
  ```sql
  -- 迁移 3 年前的数据
  INSERT INTO big_table_archive
  SELECT * FROM big_table WHERE created_at < '2020-01-01';
  
  DELETE FROM big_table WHERE created_at < '2020-01-01';
  ```

#### **2. TTL（Time-To-Live）自动清理**
• **事件调度**：定期删除过期数据。
  ```sql
  CREATE EVENT cleanup_job
  ON SCHEDULE EVERY 1 DAY
  DO
    DELETE FROM big_table WHERE created_at < NOW() - INTERVAL 3 YEAR;
  ```

---

### **六、存储引擎与参数调优**
#### **1. InnoDB 参数优化**
• **缓冲池调整**：设置为物理内存的 70%~80%。
  ```ini
  [mysqld]
  innodb_buffer_pool_size = 16G
  ```
• **日志优化**：增大日志文件，减少刷盘频率。
  ```ini
  innodb_log_file_size = 256M
  innodb_flush_log_at_trx_commit = 2  -- 非金融级事务可放宽
  ```

#### **2. 压缩表**
• **压缩存储**：对 `TEXT`/`BLOB` 较多的表启用压缩。
  ```sql
  ALTER TABLE big_table ROW_FORMAT=COMPRESSED KEY_BLOCK_SIZE=8;
  ```

---

### **七、监控与持续调优**
#### **1. 性能监控**
• **慢查询日志**：定位耗时 SQL。
  ```ini
  [mysqld]
  slow_query_log = 1
  slow_query_log_file = /var/log/mysql/slow.log
  long_query_time = 2  -- 超过 2 秒的查询
  ```
• **Prometheus + Grafana**：监控 QPS、连接数、缓冲池命中率。

#### **2. 执行计划分析**
• **EXPLAIN 解析**：优化索引和查询逻辑。
  ```sql
  EXPLAIN SELECT * FROM big_table WHERE user_id=100;
  ```

---

### **总结：优化路径选择**
| **场景**                | **优化方案**                     |
|-------------------------|----------------------------------|
| 高频查询慢               | 索引优化 + 缓存                  |
| 写入性能瓶颈             | 分库分表 + 异步写入              |
| 存储成本高               | 数据归档 + 压缩表                |
| 历史数据访问低频         | TTL 自动清理 + 冷热分离          |
| 高并发读                 | 读写分离 + 连接池优化            |

**核心原则**：  
1. **先诊断后优化**：通过 `EXPLAIN`、慢查询日志定位问题。  
2. **先低成本后高成本**：优先优化索引和 SQL，再考虑分库分表。  
3. **持续监控**：优化后需验证效果并持续跟踪。
