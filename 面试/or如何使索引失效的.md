在 MySQL 中，`OR` 运算符可能导致索引失效，尤其是在涉及多列或索引设计不合理时。以下是 `OR` 导致索引失效的常见场景、原因及优化方法：

---

### **1. OR 连接的条件中存在未索引的列**
• **原因**：如果 `OR` 两端的列中至少有一个没有索引，优化器会认为全表扫描比多次索引查询更高效。
• **示例**：
  ```sql
  -- 假设列 a 有索引，列 b 无索引
  SELECT * FROM table WHERE a = 1 OR b = 2;
  ```
  • **结果**：即使 `a = 1` 能使用索引，`b = 2` 需要全表扫描，优化器会直接选择全表扫描。

---

### **2. OR 导致索引合并（Index Merge）成本过高**
• **原因**：当 `OR` 连接的列各自有单列索引时，MySQL 可能尝试合并索引（Index Merge），但合并操作本身可能比全表扫描更慢。
• **示例**：
  ```sql
  -- 假设列 a 和列 b 均有单列索引
  SELECT * FROM table WHERE a = 1 OR b = 2;
  ```
  • **执行计划**：可能触发 `index_merge`，但对多个索引的结果取并集（`UNION`）时，若涉及大量数据，成本反而高于全表扫描。
  • **优化器决策**：若合并后的结果集过大，优化器会放弃索引，选择全表扫描。

---

### **3. OR 破坏联合索引的最左前缀规则**
• **原因**：联合索引只能按最左前缀顺序匹配，`OR` 连接的列若不在同一索引或顺序不同，会导致索引失效。
• **示例**：
  ```sql
  -- 联合索引为 (a, b)
  SELECT * FROM table WHERE a = 1 OR b = 2; 
  ```
  • **结果**：`a = 1` 能命中索引，但 `b = 2` 无法单独使用联合索引，最终全表扫描。

---

### **4. OR 与范围查询结合**
• **原因**：`OR` 连接的范围查询可能覆盖大部分数据，优化器认为全表扫描更高效。
• **示例**：
  ```sql
  -- 假设列 a 有索引
  SELECT * FROM table WHERE a > 100 OR a < 50;
  ```
  • **结果**：若数据分布中 `a > 100` 或 `a < 50` 覆盖了大部分行，索引可能失效。

---

### **5. OR 包含非等值条件**
• **原因**：非等值查询（如 `LIKE`、`!=`）本身可能无法有效利用索引，与 `OR` 结合时进一步加剧问题。
• **示例**：
  ```sql
  -- 假设列 name 有索引
  SELECT * FROM users WHERE name LIKE 'A%' OR age != 30;
  ```
  • **结果**：`name LIKE 'A%'` 可能使用索引，但 `age != 30` 导致全表扫描，最终优化器放弃索引。

---

### **优化方法**

#### **1. 用 `UNION` 或 `UNION ALL` 替代 OR**
• **原理**：将 `OR` 拆分为多个单列查询，强制使用索引。
• **示例**：
  ```sql
  -- 原始低效查询
  SELECT * FROM table WHERE a = 1 OR b = 2;

  -- 优化后（假设 a 和 b 均有索引）
  SELECT * FROM table WHERE a = 1
  UNION ALL
  SELECT * FROM table WHERE b = 2;
  ```
  • **注意**：需去重时用 `UNION`，否则用 `UNION ALL` 避免去重开销。

#### **2. 创建复合索引**
• **适用场景**：高频查询的 `OR` 条件列可合并为联合索引。
• **示例**：
  ```sql
  -- 创建覆盖列 a 和 b 的联合索引
  ALTER TABLE table ADD INDEX idx_a_b (a, b);

  -- 查询优化（需符合最左前缀）
  SELECT * FROM table WHERE a = 1 OR b = 2;
  ```
  • **限制**：仅对某些查询模式有效，需结合业务场景设计。

#### **3. 避免在 OR 中使用未索引的列**
• **强制为高频查询列添加索引**：
  ```sql
  ALTER TABLE table ADD INDEX idx_b (b);
  ```

#### **4. 使用覆盖索引**
• **原理**：若查询字段全部在索引中，即使使用 `OR`，仍可能触发索引扫描。
• **示例**：
  ```sql
  -- 索引为 (a, b, c)
  SELECT a, b FROM table WHERE a = 1 OR b = 2;  -- 覆盖索引生效
  ```

#### **5. 调整查询逻辑**
• **示例**：用 `IN` 替代部分 `OR` 条件（需注意 `IN` 的优化限制）：
  ```sql
  -- 原始查询
  SELECT * FROM table WHERE a = 1 OR a = 2 OR a = 3;

  -- 优化后
  SELECT * FROM table WHERE a IN (1, 2, 3);
  ```

---

### **通过 `EXPLAIN` 验证索引使用情况**
执行 `EXPLAIN` 分析查询计划：
```sql
EXPLAIN SELECT * FROM table WHERE a = 1 OR b = 2;
```
• **关注字段**：
  • `type`：若为 `index_merge`，表示使用了索引合并。
  • `key`：显示实际使用的索引。
  • `Extra`：若出现 `Using union`，表示索引合并为并集操作。

---

### **总结**
| 场景                  | 原因                          | 优化策略                     |
|-----------------------|-------------------------------|------------------------------|
| OR 含未索引列         | 全表扫描成本更低              | 为列添加索引或用 `UNION` 拆分 |
| OR 触发索引合并       | 合并成本高于全表扫描          | 用 `UNION` 替代              |
| OR 破坏最左前缀       | 无法命中联合索引              | 调整索引设计或拆分查询       |
| OR 结合范围查询       | 覆盖大部分数据                | 用 `IN` 或拆分条件           |

**核心原则**：尽量让 `OR` 连接的每个条件都能独立使用索引，并通过 `UNION`、索引设计或覆盖索引规避全表扫描。
