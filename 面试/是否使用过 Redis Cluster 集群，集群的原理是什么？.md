Redis Cluster 是 Redis 官方提供的分布式解决方案，用于实现数据分片和高可用性。以下是其核心原理和实现机制的详细解析：

---

### **一、Redis Cluster 的核心设计目标**
1. **横向扩展**：支持海量数据存储（TB 级别）。
2. **高可用性**：自动故障检测和主从切换（无需人工干预）。
3. **去中心化**：无单点依赖，所有节点平等（无 Proxy 层）。

---

### **二、数据分片原理：哈希槽（Hash Slot）**
#### **1. 哈希槽分配**
• **槽位总数**：16384 个槽位（0~16383）。
• **槽位分配规则**：
  • 集群初始化时，槽位均匀分配给所有主节点。
  • 示例：3 主节点集群，每个主节点管理约 5461 个槽。
• **动态调整**：
  • 支持运行时动态迁移槽位（`CLUSTER ADDSLOTS`/`CLUSTER DELSLOTS`）。
  • 槽位是数据迁移的最小单位。

#### **2. 数据路由**
• **键值定位**：
  • 对每个 Key 计算 `CRC16(key) % 16384`，得到所属槽位。
  • 客户端根据槽位映射表（Slot Map）找到对应主节点。
• **Smart Client**：
  • 客户端缓存槽位分布信息，直接连接目标节点。
  • 遇到 `MOVED` 重定向错误时，更新本地缓存。

#### **3. 槽位迁移**
• **迁移流程**：
  1. 源节点标记槽位为 `MIGRATING`，目标节点标记为 `IMPORTING`。
  2. 源节点分批发送槽位数据到目标节点。
  3. 迁移期间，客户端请求可能收到 `ASK` 重定向指令。
• **原子性保证**：
  • 迁移过程中，同一 Key 的请求会被临时阻塞，确保数据一致性。

---

### **三、高可用机制：主从复制与故障转移**
#### **1. 主从架构**
• **节点角色**：
  • 每个主节点（Master）有 1~N 个从节点（Slave）。
  • 从节点异步复制主节点数据。
• **读写分离**：
  • 默认情况下，客户端只读写主节点。
  • 可通过 `READONLY` 命令开启从节点读（需权衡一致性）。

#### **2. 故障检测**
• **Gossip 协议**：
  • 节点间通过 PING/PONG 消息交换状态信息（每秒随机通信）。
  • 每个节点维护集群元数据（节点列表、槽位分布）。
• **主观下线（PFAIL）**：
  • 节点 A 超过 `cluster-node-timeout` 未收到节点 B 的响应，标记 B 为 PFAIL。
• **客观下线（FAIL）**：
  • 超过半数主节点认为某节点 PFAIL，则触发客观下线。

#### **3. 自动故障转移**
• **从节点选举**：
  • 主节点客观下线后，其从节点发起选举。
  • 获得多数主节点投票的从节点成为新主节点。
• **槽位接管**：
  • 新主节点接管旧主节点的所有槽位，更新集群元数据。

---

### **四、集群通信与重定向**
#### **1. 客户端交互**
• **MOVED 重定向**：
  • 当客户端请求的 Key 不在当前节点槽位时，返回 `MOVED <slot> <node_ip:port>`。
  • 示例：
    ```bash
    GET user:1001
    -MOVED 1234 192.168.1.2:6379  # 提示 Key 属于槽位 1234，应访问节点 192.168.1.2:6379
    ```
• **ASK 重定向**：
  • 槽位迁移期间，目标数据可能暂存于目标节点，返回 `ASK <slot> <node_ip:port>`。
  • 客户端需先发送 `ASKING` 命令到目标节点，再重试请求。

#### **2. 集群总线（Cluster Bus）**
• **通信端口**：
  • 每个节点使用 `TCP 16379`（默认端口 + 10000）进行集群内部通信。
• **消息类型**：
  • 节点发现、故障检测、配置更新等。

---

### **五、Redis Cluster 的局限性**
1. **跨槽操作限制**：
   • 不支持跨多个 Key 的事务（如 `MGET` 多个不同槽位的 Key）。
   • 需使用 Hash Tag（`{}`）强制 Key 映射到同一槽位。
     ```bash
     # 示例：user:{1001}.profile 和 user:{1001}.orders 会被分配到同一槽位
     SET user:{1001}.profile "xxx"
     SET user:{1001}.orders "yyy"
     ```
2. **批量操作限制**：
   • Pipeline 操作需确保所有 Key 在同一节点。
3. **配置复杂度**：
   • 节点扩缩容需谨慎处理槽位迁移，避免服务中断。

---

### **六、部署与运维建议**
1. **最小集群规模**：
   • 至少 3 主 3 从，容忍单节点故障。
2. **硬件配置**：
   • 主从节点分散在不同物理机，避免单机房故障。
3. **监控指标**：
   • 槽位分布均衡性、集群状态（`CLUSTER INFO`）、主从延迟（`INFO replication`）。

---

### **七、示例：集群操作命令**
```bash
# 查看集群节点信息
redis-cli -c CLUSTER NODES

# 手动故障转移（将当前从节点提升为主节点）
redis-cli -c CLUSTER FAILOVER

# 动态添加节点
redis-cli --cluster add-node <new_node_ip:port> <existing_node_ip:port>
```

---

### **总结**
Redis Cluster 通过 **哈希槽分片** 和 **主从故障转移** 实现分布式高可用，适合大规模数据和高并发场景。其去中心化设计避免了代理层瓶颈，但需注意跨槽操作限制和运维复杂度。理解其原理有助于合理设计 Key 分布和故障恢复策略。
